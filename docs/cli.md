# Командная строка

Тот же движок, что и в интерфейсе, без браузера: повторное применение описания к новым записям, перепроверка проекта и отчёт. Результат детерминирован (без времени выполнения): повторный запуск даёт тот же вывод.

Коды возврата: **0** — всё совпало, **1** — есть отличия, **2** — ошибка (текст на стандартном потоке ошибок).

## apply — интерпретация к записям

```bash
protoledger apply --interpretation spec.yaml --input new.pcapng [--input second.pcap …] \
  [--action-log log.csv --mapping mapping.yaml] [--overlap first|last|flag] [--checksum ignore|warn|drop] \
  [--out result.json] [--strict]
```

Проект не нужен. Записи собираются по тем же правилам, что в интерфейсе (политики по умолчанию — `first` и `warn`), интерпретация применяется ко всем потокам в области применимости. В JSON: версия формата `protoledger/apply-result@1`, digest интерпретации, политики, сводка по категориям (`matched`, `violated`, `incomplete`, `ambiguous`, `unmatched`, `limit_exceeded`), для каждой записи — диагностика захвата и потоки с сообщениями: поля со статусами знания (`rule`, `hypothesis`, `unknown`), нарушения, неописанные байты. Длинные значения (больше 256 байт) усечены, `valueTruncated: true`, полная длина — в `len`.

Если передан журнал действий (`--action-log` + `--mapping`, колонки сопоставляются так же, как в API), гипотезы интерпретации с `test` проверяются на нём: в результате `hypotheses` — выполнилась ли на k из n применимых примеров, контрпримеры с якорями.

Без `--out` результат идёт в стандартный вывод, краткая сводка — в stderr. `--strict`: код 1, если есть сообщения не в категории `matched`.

Эталонные результаты на записях стенда лежат в `fixtures/stand/expected/`; тест сверяет с ними вывод `apply` (`BLESS=1 cargo test -p protoledger --test cli` обновляет после проверки глазами).

## verify — перепроверка проекта

```bash
protoledger verify my-research.protoledger [--run run-0001]
```

1. Копии записей в `sources/` сверяются с sha256 (изменена — отличие).
2. Каждый сохранённый прогон (или указанный) выполняется заново на тех же входах — ревизия интерпретации, фильтры корпуса, записи — и сравнивается с сохранённым: сводка, таблицы сообщений, контрпримеры. Совпало — `результат воспроизводится`, иначе показано, что изменилось; если настройки сборки потоков изменены после прогона, это указано отдельно.

Проект можно скопировать в другую папку и проверить там: пути внутри проекта только относительные.

## report — отчёт по проекту

```bash
protoledger report my-research.protoledger [--run run-0001] [--format md|html] [--out report.html]
```

Без `--out` отчёт идёт в стандартный вывод. Без `--run` берётся последний прогон; устаревший помечается в тексте. Код возврата 0, если отчёт собран.

В отчёте:

- **область применимости** — записи с sha256, размерами, числом кадров и соединений, диагностика захвата, журналы действий, ревизия и область интерпретации; выводы справедливы только для них;
- **результат проверки** — сообщения по категориям и типам, байты, которые описание не объясняет, контрпримеры с якорями (поток, диапазон, sha256);
- **гипотезы** — статус, основания (наблюдения), тест и его итог (формулировка «выполнилась на N из M, контрпримеров нет», не «доказано»);
- **наблюдения** с состоянием якорей, **открытые вопросы**;
- как воспроизвести результат (`verify`, `apply`).

HTML самодостаточен: всё из данных экранировано, скриптов и внешних ресурсов нет, политика CSP — в `<meta>`. В Markdown разметка из данных экранируется.
Тот же отчёт отдаёт `POST /api/reports`.

## Перенос проекта на другую машину

Проект — папка (ADR 0013: zip-экспорта нет). Перенос: скопировать папку `.protoledger` целиком (подкаталог `.cache/` не обязателен — он пересобирается), открыть её в интерфейсе или проверить:

```bash
protoledger verify /путь/к/скопированному.protoledger
```

Копии записей сверяются с sha256, прогоны выполняются заново и сравниваются с сохранёнными. Внутри проекта только относительные пути, поэтому результат и отчёт (`report`) не зависят от места и машины; это проверяет тест CI (копия в другую папку → `verify` и `report` дают то же).

## bench — время и память

```bash
cargo run -p pl-synth --release -- profile --out bench-data/profile.pcapng   # 1000 соединений, 250 тыс. кадров, около 100 МиБ
protoledger bench bench-data --interpretation fixtures/synthetic/interpretation.yaml [--repeat 3] [--json]
```

Для каждой записи (файл или каталог с `.pcap`/`.pcapng`, без вложенных) печатает размер, число кадров и соединений, время этапов — чтение файла, индексация кадров, сборка потоков, применение описания (если оно задано) — и скорость разбора в МиБ/с. С `--repeat N` берётся лучшее время этапа. В конце — пик памяти процесса (`VmHWM` из `/proc/self/status`; на системах без `/proc` — `null`). Время и память зависят от машины, поэтому результат не детерминирован; официальные цифры снимаются на профиле 4 vCPU / 8 ГиБ (`docker run --cpus=4 --memory=8g`).
