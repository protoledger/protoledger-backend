# API

Описание для людей. Источник истины для кода — [`openapi.yaml`](openapi.yaml); интерактивная документация — `/api/docs` запущенного приложения (только dev-сборка).
Правило: меняется контракт — в том же PR обновляются оба файла. CI проверяет, что каждый путь из `openapi.yaml` описан здесь.

Версия контракта: **0.1.7** (фаза Ф1: открыть запись → соединения → поток → байт → кадр).

## Общее

| | |
|---|---|
| Базовый URL | `http://localhost:8080/api` |
| Формат | JSON, поля в `camelCase`; смещения и длины — целые числа |
| Время | строка RFC 3339 в UTC с наносекундами: `2026-10-09T12:00:00.250000000Z` — время захвата из записи |
| Байты | base64 внутри JSON |
| Ошибки | [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457), `application/problem+json`: `type`, `title`, `status`, `detail` (по-русски) |
| Долгие операции | создают задачу (`202` + `jobId`), прогресс — SSE `/api/jobs/{id}/events`, отмена — `DELETE /api/jobs/{id}` |
| Списки | `limit` (1–500, по умолчанию 50) и `offset`; ответ `{items, total, limit, offset}`, порядок стабильный |

### Защита запросов

Проверяются **все** запросы (в том числе страница интерфейса), по порядку:

1. `Host` — только `127.0.0.1`, `localhost`, `[::1]` (порт не сверяется: Docker публикует другой), иначе `403`. Защита от DNS rebinding.
2. `Origin` (если есть) — только свой (тот же адрес, что в `Host`), иначе `403`. В dev-режиме дополнительно разрешён `http://localhost:3000`.
3. Для `/api/*` — заголовок `X-Protoledger-Token` с токеном сессии, иначе `401`. Исключения: `GET /api/health` (отдаёт только статус и версию — на него смотрит healthcheck Docker) и `/api/docs/*` в dev-сборке.

Токен — 256 бит из системного генератора случайных чисел, новый при каждом запуске. Движок кладёт его в отдаваемый `index.html`: `<meta name="protoledger-token" content="…">`. Если в собранном интерфейсе этого тега нет, движок добавляет его в `<head>`; если есть значение-заглушка `__PROTOLEDGER_TOKEN__`, подставляет токен на её место. Клиент добавляет токен в каждый запрос в одном месте. Страница `index.html` отдаётся с `Cache-Control: no-store`. CORS-заголовков нет.

Каждый ответ содержит `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`. Поэтому в собранном интерфейсе нельзя использовать встроенные (inline) скрипты и внешние ресурсы.

Пределы: тело JSON — 8 МиБ (`413`), одновременных задач — 2 (`429`), SSE-поток живёт не дольше 30 минут (клиент переподключается и сразу получает текущее состояние). `EventSource` не умеет заголовков, поэтому SSE читается через `fetch` со стримом.

## Документация и dev-режим

Только в dev-сборке (cargo-feature `dev-tools`, ADR 0011); в релизной сборке этого кода нет.

```bash
PROTOLEDGER_DEV_TOKEN=dev-token-123 cargo run -p protoledger --features dev-tools -- serve --dev
```

- Swagger UI — http://localhost:8080/api/docs, «Try it out» сам подставляет `X-Protoledger-Token`.
- Контракт — http://localhost:8080/api/docs/openapi.yaml, то же даёт `protoledger openapi`.
- `--dev`: токен берётся из `PROTOLEDGER_DEV_TOKEN` (от 8 символов: латиница, цифры, `-`, `_`), разрешён origin `http://localhost:3000` (dev-сервер фронта). Без `--dev` послаблений нет.
- Релизный бинарник проверяет `scripts/check-release-clean.sh`.

### Идентификаторы

| Что | Вид | Пример |
|---|---|---|
| Запись | sha256 содержимого, 64 hex | `3f5a1c0d…f9e8d` |
| Импорт | `imp-NNNN` | `imp-0001` |
| Соединение | `<первые 8 hex sha256>:cNNNN` | `3f5a1c0d:c0001` |
| Направленный поток | `<соединение>:ab` (от `a` к `b`) или `:ba` | `3f5a1c0d:c0001:ab` |
| Кадр | `(sha256 записи, frameNo)`, номера с 1 как в Wireshark | `7` |
| Задача | `job-NNNN` | `job-0001` |

Идентификаторы содержат `:` — в пути оставляются как есть.

### Поток и карта сегментов

`GET /api/streams/{stream}/bytes?from=0&len=4096` возвращает участки подряд, они покрывают запрошенный диапазон без пропусков:

| `status` | Смысл | `data` |
|---|---|---|
| `data` | Байты есть в записи | base64 |
| `gap` | Байтов нет (потеря, усечение). Нули не подставляются | `null` |
| `ambiguous` | Перекрытие с разными байтами; `data` — вариант по политике проекта (`first`, `last`), `variants` — все варианты | base64; `null` при политике `flag` |

Каждый участок несёт `frames` — кадры-источники (с признаком `duplicate` для повторов). Диапазон за концом потока усекается, `length` — фактическая длина. `len` не больше 1 МиБ.

### Интерпретация и предпросмотр

Интерпретация — YAML `protoledger/interpretation@1` (ADR 0005): фрейминг, сообщения с условием `when`, поля со статусами `rule` / `hypothesis` / `unknown`, гипотезы, проверки. Каждое сохранение, меняющее смысл, — новая ревизия (`rev` с 1, `digest` — sha256 канонической формы); старые ревизии не меняются.

`POST /api/interpretation/preview` возвращает по каждому сообщению потока категорию:

| `category` | Смысл |
|---|---|
| `matched` | Сообщение выделено, тип найден, поля разобраны, проверки прошли |
| `violated` | Нарушено правило (`status: rule`) или ожидание; нарушение гипотезы сообщение таким не делает |
| `incomplete` | Сообщение задевает дыру или обрывается в конце потока; по неполным данным нарушений не объявляется |
| `ambiguous` | Задевает неоднозначный участок |
| `unmatched` | Ни одно описание не подошло |
| `limit_exceeded` | Ограничение реализации: заявленная длина больше предела 16 МиБ, разбор потока остановлен |

`unknownBytes` — байты вне описанных полей и в зонах `unknown`: «чего мы ещё не знаем» видно в числах. Ошибка в тексте интерпретации — `422` с описанием места и причины. Значения: `valueType` `int` (число; за пределами ±2^53 — десятичная строка), `bool`, `string`, `bytes` (hex-строка).

### Наблюдения и гипотезы

**Наблюдение** — якорь на байты потока (запись, поток, диапазон, sha256 байтов) и комментарий. Если при другой политике сборки байты по якорю изменились, `anchorState` становится `broken`: наблюдение не «переезжает» молча.

**Гипотеза** — утверждение с основаниями (наблюдениями), тестом-выражением и статусом `proposed` / `supported` / `refuted` / `superseded`. Статус ставит исследователь; `POST /api/hypotheses/{id}/test` его не меняет. Тест применяется к сообщениям всех записей по сохранённой интерпретации и может ссылаться на поля сообщения, поля парного ответа (`response.*`), параметры и результат действия из журнала (`action.params.*`, `action.result.*`):

```
value == action.params.value        # значение в запросе равно параметру действия
response.applied == action.params.value
```

Итог — не «доказано», а одно из: `no_counterexample` (выполнилась на `held` из `applicable` применимых примеров, контрпримеров нет), `refuted` (есть контрпример с якорем и значениями) или `untested` (применимых сообщений нет). Сообщения, для которых в данных нет нужного поля или действия, в счёт не идут и показываются как `notApplicable`.

**Вопросы** — открытые вопросы исследователя; попадают в отчёт.

### Журнал действий и поиск обмена

Формат журнала от организаторов заранее неизвестен, поэтому импорт универсален: CSV с произвольными именами колонок, которые сопоставляются явно (`mapping`: `time`, `action`, `params`, `result`), несколько форматов времени (`rfc3339`, Unix в с/мс/мкс/нс), поясом для времени без пояса (`utcOffsetMinutes`) и **поправкой на сдвиг часов** клиента (`clockOffsetMs`). Параметры и результат — `ключ=значение;…` или JSON; слово без значения в результате (`ok;applied=21`) становится `status`. Строки, которые не разобрались, видны в `errors`; если разобрана меньше половины — `422`.

Действие определяется журналом и номером строки (`line`). `GET …/actions/{line}/exchange` возвращает кадры с данными и, при сохранённой интерпретации, сообщения всех записей проекта в окне от `before` мс до и `after` мс после времени действия. Это помощь в поиске, а не вывод: совпадение по времени — основание для наблюдения, а не доказательство связи.

### Прогоны проверки

`POST /api/runs` применяет сохранённую интерпретацию к корпусу — потокам записей проекта с фильтрами (`sources`, `direction`, `port`; фильтры сохраняются в прогоне и видны рядом со сводкой). Прогон — задача; готовый прогон неизменен.

- **Сводка** — по всему набору: сообщения по категориям (`matched`, `violated`, `incomplete`, `ambiguous`, `unmatched`, `limit_exceeded`), потоки вне области применимости, разбивка по типам сообщений, неописанные байты (`unknownBytes`). Неполные, неоднозначные, не охваченные и неподдерживаемые сообщения не прячутся за общей цифрой.
- **Контрпримеры** — данные, на которых нарушено правило или гипотеза: якорь (запись, поток, диапазон, sha256 байтов), категория, нарушения с причиной. Хранится до 1000, счётчик — полный.
- **Устаревание** — прогон подписан digest интерпретации, digest настроек сборки и записями корпуса. Если интерпретацию или настройки изменили, а записи пропали из проекта, `stale: true` и `staleReasons` называют причину. Такой прогон остаётся читаемым, но не выдаётся за актуальный.
- **Сравнение** `GET /api/runs/diff?a=…&b=…`: сообщения сопоставляются по потоку и началу; итог — исправлено, ухудшено, изменено, добавлено, исчезло, без изменений.

### Отчёт

`POST /api/reports` собирает отчёт из текущего состояния проекта: записи и их sha256 (область применимости), диагностика захвата, интерпретация, результат прогона с контрпримерами, гипотезы (статус, основания, результат теста), наблюдения, открытые вопросы. Без `runId` — последний прогон; устаревший помечен в тексте. Текст приходит строкой `content`: фронт сохраняет её файлом `fileName` или показывает как текст, но не вставляет HTML в страницу. HTML отчёта сам по себе безопасен (экранирование, без скриптов и внешних ресурсов), его открывают как файл. Тот же отчёт даёт команда `protoledger report <проект> --format md|html [--out файл]`.

### Задачи и SSE

Состояния: `queued` → `running` → `succeeded` | `failed` | `cancelling` → `cancelled`. Результат (`result`) — только у `succeeded`, ошибка (`error`, Problem) — только у `failed`.

`GET /api/jobs/{id}/events` — `text/event-stream`:

| Событие | Данные | Когда |
|---|---|---|
| `progress` | `{jobId, stage, done, total, unit}` | по ходу выполнения |
| `state` | `Job` | при смене состояния и первым событием после подключения |

Поток закрывается после терминального состояния. `stage`: `reading` → `reassembling` → `saving` → `done`. `total = 0` — пока неизвестно.
Во время импорта соединения и потоки доступны сразу, по мере готовности.

## Сценарии

### «Открыть запись → соединение → поток → байт → кадр»

1. `POST /api/project` `{"path": "/workspace/demo.protoledger", "mode": "create"}` — `200`, проект создан.
2. `POST /api/sources` `{"path": "/workspace/captures/session-1.pcapng"}` — `202 {"jobId": "job-0001"}`.
   Браузер вместо пути отправляет `multipart/form-data` с полем `file`.
3. `GET /api/jobs/job-0001/events` — `progress` с этапами, в конце `state` = `succeeded` и `result.sourceSha256`.
   Прогресс можно опрашивать и через `GET /api/jobs/job-0001`; отмена — `DELETE /api/jobs/job-0001`.
4. `GET /api/connections?source=<sha256>&limit=50` — таблица соединений: адреса, время, признаки (`gaps`, `retransmissions`…), два потока с длинами.
5. `GET /api/streams/3f5a1c0d:c0001:ba/bytes?from=0&len=4096` — байты потока и карта сегментов (где дыры и повторы).
6. Клик по участку потока → `frames[].frameNo` → `GET /api/frames/<sha256>/7` — заголовки, байты кадра, `payload` внутри кадра и `streamRange` обратно в поток.
7. Что не разобрано в записи: `GET /api/sources/<sha256>/diagnostics`.

### Открытие существующего проекта

`POST /api/project` с `mode: open` сбрасывает записи прежнего проекта и запускает фоновую задачу, которая заново разбирает записи из `sources/`. Они появляются в `GET /api/sources` по мере готовности; ход виден в `GET /api/jobs`. Пока задачи идут, сменить проект нельзя (`409`).

### Повторный импорт того же файла

`POST /api/sources` с тем же файлом создаёт новый импорт (`importId` растёт), записи не склеиваются.

## Коды ошибок

`type` всегда вида `urn:protoledger:problem:<код>`.

| `type` | HTTP | Когда | Что делать клиенту |
|---|---|---|---|
| `unauthorized` | 401 | Нет или неверный `X-Protoledger-Token` | Перечитать токен из `<meta>`, перезагрузить страницу |
| `forbidden` | 403 | Чужой `Host` или `Origin` | Открывать приложение по адресу движка |
| `bad-request` | 400 | Неверный параметр, тело, путь вне допустимого (`len` > 1 МиБ, `..` в пути) | Показать `detail`, исправить ввод |
| `not-found` | 404 | Нет такой записи, потока, кадра или задачи | Обновить список |
| `no-project` | 409 | Проект не открыт | Показать выбор проекта |
| `conflict` | 409 | Задача уже завершена; у закрываемого проекта идут задачи | Обновить состояние |
| `limit-exceeded` | 413 | Файл или тело больше защитного предела; в `limit` — имя, значение, единица | Показать предел и подсказку |
| `unsupported-media` | 415 | Тело не JSON и не `multipart/form-data` | Исправить клиент |
| `unprocessable` | 422 | Файл не PCAP/PCAPNG, папка не проект, формат проекта новее движка | Показать `detail` |
| `too-many-jobs` | 429 | Уже идёт 2 долгие задачи | Дождаться, повторить |
| `internal` | 500 | Непредвиденная ошибка; сервер продолжает работать | Показать `detail`, предложить повторить |

Замечания к записи (IPv6, усечённые кадры, неверные суммы…) — не ошибки запроса: это `diagnostics` записи и кадра, импорт при них успешен. Кадры вне Ethernet/IPv4/TCP тоже попадают в диагностику: `non_ip` (ARP и др.), `non_tcp` (UDP, ICMP), `ipv6_skipped`, `ip_fragment`.
